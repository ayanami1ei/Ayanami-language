## 一、统一引用关系模型（Extensible Reference Model）

### 1. 设计目标

将引用从特定的内存表示（如指针）提升为一种由编译器理解、允许用户扩展的语言级语义。

当前语言和业务代码中存在多种本质上具有引用作用的机制：

- 内存地址与普通指针；
- ID、索引和句柄；
- 通过哈希表、注册表或对象管理器查找目标；
- 用户自定义的对象引用与反向映射；
- 未来可能支持的远程引用或其他间接访问机制。

这些机制都能表达“通过某种表示访问另一个对象”的关系，但目前通常需要分别实现访问、
生命周期管理、失效处理、序列化及优化逻辑。

目标是将它们统一到一个可扩展的引用语义模型中，让用户能够定义自己的引用表示和解析
方式，同时让编译器识别并分析这些关系。

### 2. 核心模型

探索类似 `Ref<T, U>` 的模型：

- `T`：目标对象或被引用对象的类型；
- `U`：引用表示的类型，例如指针、ID、句柄或用户自定义类型；
- 引用关系支持从 `T` 获取对应的引用表示 `U`，并在满足相应约束时从 `U` 解析到 `T`。

示意关系：`T ↔ U`。该符号表示可建立正向和反向引用关系，不代表两者必然构成严格的
一一映射，也不代表解析永远成功。

需要允许不同的底层实现，例如：

- 直接使用 C 风格指针；
- 使用 ID 加哈希表；
- 使用索引与 generation 组成的句柄；
- 使用用户定义的结构和解析算法。

**统一的是引用关系的语义，而不是强制统一底层存储表示或访问成本。**

### 3. 编译器应理解的语义

未来需要研究如何让引用协议向编译器提供足够的信息，以支持：

- 目标类型和目标身份分析；
- 生命周期与引用有效性检查；
- 所有权、借用、共享访问和独占修改约束；
- 引用失效条件及对象销毁规则；
- 别名分析与访问冲突判断；
- 引用解析的重复计算消除；
- 静态特化、内联及其他合法的编译优化；
- 自动生成或辅助生成序列化、反序列化和引用映射逻辑。

用户自定义引用不能仅仅是普通函数接口。需要探索如何将引用关系作为编译器可识别的
语义信息保留到 IR，而不只是降级为普通函数调用。

同时，编译器不能无条件相信用户提供的保证。需要区分静态可证明的约束、运行时检查和
用户实现契约。

### 4. 重点应用场景

- 将对象 ID、句柄和指针纳入统一的引用模型；
- 支持树、图、对象池等复杂对象关系；
- 统一对象引用的序列化与反序列化；
- 让 ID 引用、数据库外键和其他业务关联获得统一的类型与关系信息；
- 允许用户扩展新的引用实现，而不必重复实现所有通用基础设施；
- 让编译器能够分析过去只存在于业务逻辑中的引用关系。

例如，可以探索让对象 ID 作为一种具有明确目标类型的引用表示，使 JSON 中的 ID 不再
只是普通整数，而是能够参与类型检查和对象关系重建的引用信息。

需要区分序列化引用与序列化完整对象图，并考虑失效 ID、循环引用、多对一关系及反向
映射不唯一等问题。

### 5. 设计原则

1. 不要求所有引用都使用原始指针。
2. 不要求所有引用都使用同一套运行时解析机制。
3. 不将引用关系与所有权、生命周期等语义混为一谈。
4. 不因统一抽象而强制引入动态分派或额外运行时开销。
5. 允许编译器根据已知条件将抽象引用优化为直接内存访问或其他更高效的实现。

## 二、统一环境注入模型（Environment Injection）

### 1. 设计目标

为 Ayanami 探索一种由编译器支持的环境依赖声明和自动传递机制。

当前，函数或对象依赖的资源往往需要通过显式参数层层传递，或者通过全局变量、隐式
默认资源等方式获取。

显式传参虽然清晰，但容易产生大量重复代码；全局资源虽然方便，却不利于局部替换、
依赖分析和成本控制。

目标是在保持依赖可见、成本明确和类型安全的前提下，让用户声明所需环境，由编译器
自动进行环境传播和实现选择。

### 2. 示例语法

探索类似以下语法：

`#[env::alloc]`

用于声明某个类型、字段或操作需要分配器环境。

例如（示例仅表达设计意图，具体语法与字段语义尚未确定）：

```rust
struct Image {
    #[env::alloc]
    allocator: Allocator,

    pixels: Vec<Pixel>,
}
```

外层可以选择具体环境：

```rust
#[env::alloc = arena]
fn process_images() {
    let a = load_image(path_a);
    let b = load_image(path_b);
}
```

如果内部调用链需要同类环境，编译器可以自动传播该环境，而不必让每个函数都显式接收
和转发分配器参数。

### 3. 环境依赖的核心语义

需要将以下概念区分开来：

- **环境需求**：函数或类型需要什么资源或能力；
- **环境提供**：具体由哪个实例满足该需求；
- **环境传播**：调用链如何传递环境需求；
- **环境覆盖**：内层如何显式选择其他实现；
- **资源绑定**：对象是否需要持有资源，并在其生命周期内继续使用该资源。

环境需求可以探索为一种编译期可分析的隐式泛型约束。

当具体环境类型在编译期已知时，编译器可以考虑静态派发、单态化、内联及其他特化优化；
当环境实例在运行时才确定时，也可以采用显式的环境引用或其他运行时表示。

不能假定所有环境注入都必然零成本。

### 4. 以自定义内存分配器为首个应用

当前优先探索的应用是可自定义内存分配器。

设计目标：

- 用户能够自由选择系统堆分配器、Arena、固定容量分配器或其他自定义分配器；
- 库代码只声明需要分配器，不必为每个分配操作手动传递参数；
- 外层函数或类型可以提供具体的分配器环境；
- 内层调用自动继承环境，也可以显式覆盖；
- 环境依赖可见，用户能够知道资源从何而来；
- 编译器能够检查资源生命周期，并在可能时优化环境传递；
- 不强制使用全局默认分配器，也不要求所有函数都重复声明和传递分配器。

需要特别区分：环境依赖不一定意味着对象必须存储分配器实例。若容器在后续扩容或销毁
时仍需使用原分配器，则必须通过明确的资源绑定或类型语义保证这一点。

### 5. 环境传播与类型系统

研究将环境需求视为一种可传播的静态约束：

- 函数调用所需环境必须得到满足；
- 中间函数可以继承环境，而不必手动转发参数；
- 函数可以声明自己需要的环境，或将需求留给调用者满足；
- 同一环境需求存在多个候选提供者时，应要求明确选择，避免静默歧义；
- 泛型、类型推导和编译期分析应能够参与环境解析。

环境传播不应依赖运行时搜索父对象或全局查找，除非具体环境策略明确要求这样做。

### 6. 可扩展方向

内存分配器只是首个应用。未来可研究将同一套环境机制用于：

- 日志和诊断；
- I/O 能力；
- 资源管理器；
- 内存池和对象池；
- 数据库或其他外部资源；
- 其他适合显式声明依赖、由调用上下文提供实现的能力。

这些资源可以共享环境传播和检查机制，但不应被强行赋予相同的生命周期、所有权或
副作用语义。

## 三、两个方向的统一关系

引用关系模型与环境注入模型可以共享编译器内部的环境传播、约束检查和 IR 分析基础
设施。

- 引用模型关注：如何表示、解析和维护对象之间的引用关系。
- 环境注入关注：某项操作需要什么资源或能力，以及如何获得这些资源。
- 编译器负责：分析依赖、检查约束、传播环境，并根据可证明的信息进行优化。

二者可能相互配合。例如，引用解析可以依赖对象注册表环境；分配器环境也可能决定某些
对象的资源绑定方式。

但不能因此将引用关系、环境依赖、所有权和 effect 合并成一个没有区分的万能抽象。
应当统一底层分析机制，同时保留各自的语义边界。

## 四、规划阶段的实现原则

1. 当前先记录设计方向，不立即实现。
2. 不提前锁定 `Ref<T, U>`、`#[env::alloc]` 等示例语法。
3. 优先设计语义契约，再确定语法、类型规则和 IR 表示。
4. 保证用户自定义扩展能够被编译器分析，而不只是包装普通函数。
5. 保持成本可理解，避免因抽象而无意引入动态分派、查找或额外内存开销。
6. 明确区分静态保证、运行时检查和用户实现契约。
7. 先以简单指针引用和自定义分配器验证模型，再扩展到 ID、对象图、序列化和更复杂的
   环境。

**长期目标：让引用关系与环境依赖成为 Ayanami 中可扩展、可静态分析、可参与编译优化
的语言级概念，从而减少业务代码中的重复机制，同时保留明确的语义、安全约束与性能
成本。**
